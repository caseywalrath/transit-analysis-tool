# Road network

Reference detail moved verbatim from `CLAUDE.md`. Read the code when this and the code disagree.

## Files

- **`walk-cost.js`** — Intersection crossing-penalty classification + cost math (`window.WalkCost`, same engine-namespace convention as `window.ConnectorGraph`/`window.Travelshed`/`window.TPI`). No turf/DOM/Map/App state — plain values in/out so the golden harness loads it directly (`docs/walkshed-bands-and-crossing-penalties-plan.md` Phase 4). `roadTier(hwy)` classifies an OSM `highway` value as `"major"` (primary/secondary + their `_link` ramp forms) or `"minor"` (everything else, including `tertiary` — deliberately, since it's usually an unsignalized collector; unknown/absent classes also default to `"minor"`). `nodeTier(hwyList)` takes the highway classes of every edge meeting at one node and returns `"major"`/`"minor"`/`null` — `null` when fewer than 3 edges meet (a shape point or dead end, not a real intersection), which is what keeps the penalty off the vast majority of geometry vertices. `penaltyKm(tier, {majorSec, minorSec, speedKmh})` converts a fixed-seconds delay into a km distance the flood can subtract from its budget (`speedKmh * sec / 3600`), so the penalty stays a constant wall-clock delay regardless of walk speed; returns 0 for a null tier or a zero/absent penalty or speed. Node-uniform, not turn-aware — a deliberate, documented approximation (over-charges travel *along* an arterial); motorway/trunk classes never reach this file since they're already `pedBlocked` upstream in `road-network.js`. Golden-tested in `test/cases/walk-cost.mjs`. Consumed by `road-network.js`'s flood starting Phase 5.

- **`network-store.js`** — Road-network IndexedDB store (`App.networkStore`). The downloaded street network is the one piece of session state that is both expensive to reacquire (the public Overpass endpoint fails often enough that 3-4 retries is routine) and far too large for `localStorage` (tens of MB), so it gets its own IndexedDB database — `mat-network-cache`, store `networks`, keyed by `id`, with a `savedAt` index — rather than riding the session cache in `cache.js`. Records are `{ id, savedAt, source: "overpass"|"file", label, featureCount, extent (Feature<Polygon>|null), geojson (JSON string) }`. API: `supported()`, `save(record)`, `latest()`, `clear()`, `MAX_ENTRIES` (3). Everything is strictly an optimization — the in-memory network is already built and usable whether or not a write lands, and browsers may evict IndexedDB under storage pressure at any time — so every failure path is swallowed (logged at most) and callers always fall back to a fresh download. `save()` writes then prunes oldest-first to `MAX_ENTRIES`; a failed write (quota exceeded being the realistic case at this size) retries exactly once after dropping every OTHER stored network, then gives up quietly. `latest()` reads the `savedAt` key list first and fetches only the winning record, so the other stored networks' geojson strings are never deserialized. **The `_withStore(mode, fn)` helper exists for a correctness reason, not tidiness:** an IndexedDB transaction deactivates as soon as control returns to the event loop, so `await`ing one request and then touching the store again throws `TransactionInactiveError` whenever the main thread is busy enough to push the continuation past a task boundary — which is exactly page startup, the moment this store exists to be read at. `fn` therefore must issue its requests synchronously, or from another request's `onsuccess` (where the transaction is still active), and never after an `await`. The Recent Projects store in `cache.js` uses the older `_idbTx`/`await` shape; do not copy it here.

- **`road-network.js`** — Offline routing/graph engine: Overpass download → graph → Dijkstra. `App.roadNetworkLoaded()`/`roadNetworkEpoch()`, `findLocalRoute` (driving), `computeWalkshed`/`computeWalkCostMap` (walking isochrones), `fetchRoadNetwork`/`loadRoadNetworkFromFile`/`clearRoadNetwork`, `App.getWalkNetworkSegments()` (plain-array, epoch-cached view of every non-`pedBlocked` segment, tagged `kind: "base"|"connector"` — consumed by `network-connectors.js`'s reference layer; see `docs/network-connectors-plan.md`). **Sidewalk-data capture (`docs/sidewalk-data-plan.md` Phase 1):** the Overpass parse loop reads three more tags per way — `sidewalk`, `footway`, `crossing` — plus the element id as `wayId`; `out geom;` already returns all tags and the id, so this is parse-side only and adds nothing to the download. `buildGraph` carries `sidewalk`/`footway`/`wayId` onto each `_segmentIndex` entry (defaulting to `""`/`""`/`null` for a legacy import) but deliberately **not** onto `addGraphEdge`'s edge objects — edges are allocated twice per segment in the hot routing path and nothing reads these fields until Stage D. `getWalkNetworkSegments()` carries the same three fields plus `hwy` on its returned records, additive to the existing `coords`/`kind` shape. **Network Connectors overlay (Phase 4, crossings added in Phase 5):** a private `rebuildNetwork()` — `buildGraph(_roadGeoJSON)` → `applyConnectorOverlay()` → one `_networkEpoch++` — is the single choke point every base-network load (`fetchNetworkForBounds`/`loadRoadNetworkFromFile`) AND every connector change (`App.setNetworkConnectors(connectors, opts)`) routes through, so connectors are never merged into `_roadGeoJSON` and always survive a wholesale base replacement. `applyConnectorOverlay()` gathers candidate base segments near the connectors from `_segGrid` (same cell-range technique `snapToNetwork` uses, expanded by 1 cell), calls `window.ConnectorGraph.planarizeConnectors(...)` with `splitCrossings: true` (Phase 5 — a connector crossing a street mid-block joins it there, not just at welded endpoints; `pedBlocked` candidates — motorways/trunks — are still skipped for both crossing splits and welding, the bridge/freeway mitigation from the plan's §1), removes the replaced base segments' graph edges, and adds the returned edges tagged `pedBlocked: false, carBlocked: true` — connector edges are walk-only and never affect `findLocalRoute` (driving). `_segGrid` is rebuilt wholesale from the final `_segmentIndex` afterward, and so is `_nodeTier` (see the crossing-penalty paragraph below) since a connector split can turn a 2-degree curve point into a real intersection. Returns `{ reason: "no-base-network" }` when no network is loaded, or `{ addEdges, removeSegIds, joins, orphans }` (counts + the raw `ConnectorGraph` join/orphan records, `joins[].kind` now including `"crossing"` as well as `"weld"`) otherwise — stashed as the return value of `App.setNetworkConnectors()`, which `network-connectors.js` caches as the connection report; `App.getLastConnectorOverlayReport()` is a raw accessor for the same value, used by `network-connectors.js` to re-sync its cache after a base-network reload that didn't go through `setNetworkConnectors()` (Phase 6). **Offline persistence:** every successful download/import calls the private `persistNetwork(id, source, label)`, which stores the built network in `network-store.js` (deferred by one `setTimeout(0)` — serializing a city-scale network blocks for a few hundred ms and nothing downstream waits on it). Overpass records are keyed by `extentCacheId(extentPolygon)` (the extent bbox rounded to 3 decimals) so re-downloading an area replaces its stored copy instead of accumulating near-duplicates; imports key on `"file:"+name`. `App.restoreCachedNetwork()` rebuilds from the most recent stored record at startup, and `clearRoadNetwork()` also empties the store — clearing is an explicit "remove this" action (Add Data × icon, Clear all features, Reset Session, all confirm-gated), so a cleared network must not silently resurrect on the next refresh. See the App Namespace section below for the full export list.

- **`network-connectors.js`** — Network Connectors App-level orchestration (`docs/network-connectors-plan.md`). **Phase 1:** a discreet, hideable "Walk network" reference layer (source `walk-network` / layer `walk-network-line`) built from `App.getWalkNetworkSegments()`, so a user can see the walkable network before drawing a connector. `App.refreshWalkNetworkLayer()` is called from `road-network.js`'s `updateUI()` on every load/import/clear, and from `refreshNetworkConnectors()` below after every overlay rebuild. Styled discreetly (`#94a3b8`, width 1, opacity 0.45) and inserted below drawn features, following the GTFS shapes-layer precedent. Registered in `layers-panel.js` `REFERENCE` as "Walk network", right after "Road download area". **Phase 4:** owns `App.networkSettings = { snapToleranceFt: 50 }` — one global value shared by Walkshed and Transit Travelshed (never per-module state; see the plan's §2 "Known conflict"), persisted as an additive `networkSnapToleranceFt` session-cache field (`cache.js`, same pattern as `featureSortMode`). `collectConnectorLines()` scans `App.lines` for `attributes.networkRole === "connector"` (skipping hidden features) and returns plain `{ id: "line:"+idx, coords }` — the only place App.lines is translated into the plain geometry `road-network.js` consumes. `App.refreshNetworkConnectors()` computes a cheap `JSON.stringify` signature from the collected geometries + tolerance, no-ops when unchanged, and otherwise calls `App.setNetworkConnectors(connectors, {snapToleranceKm})` (`ft * 0.0003048`), caches the returned report, and refreshes the walk-network layer — safe to call liberally (from `App.notifyProject()`, line vertex drag-**end** in `editing.js`, the `networkRole` field's `onChange` in `feature-attributes.js`, and the snap-tolerance inputs in the Walkshed/Transit Travelshed Advanced blocks) with no debouncing needed. `App.getConnectorReport()` returns the last cached report. **Phase 5** flips `splitCrossings: true` in `road-network.js` (see that entry). **Phase 6** adds a `network-joins`/`network-joins-point` circle layer (crossing/weld dots + hollow amber orphan circles) built by `refreshJoinMarkers()` from the same cached report and registered on this same "Walk network" Layers-panel row's `layers` array (not a separate row — see `layers-panel.js` below), plus `App.getConnectorReportSummary()` for the Walkshed/Transit Travelshed results-footer line — full detail in the App Namespace section below.

- **`walk-audit.js`** — Sidewalk-data audit engine (`window.WalkAudit`, same engine-namespace convention as `window.WalkCost`/`window.ConnectorGraph`/`window.Travelshed`), `docs/sidewalk-data-plan.md`. Same split-in-two file shape as `walk-cost.js`/`layer-palettes.js`: a pure block (no turf/DOM/Map/App, golden-tested) followed by an App-level block that reads `App.*` only at call time. **Pure (Phase 2):** `classifySidewalk(seg)` → `"footway"` (the segment IS mapped sidewalk/footway/path/steps/pedestrian/cycleway geometry — a separate way, so the centerline `sidewalk=` attribute doesn't apply) | `"both"` (`sidewalk=both|yes`) | `"one-side"` (`sidewalk=left|right`) | `"none"` (`sidewalk=no|none|separate`) | `"unknown"` (anything else or absent — the common case on a lightly-mapped street). Takes a plain `{footway, hwy, sidewalk}` object, returns a string. **App (Phase 2):** `App.refreshSidewalkCoverageLayer()` builds a FeatureCollection from `App.getWalkNetworkSegments()` (source `sidewalk-coverage` / layer `sidewalk-coverage-line`, create-once/`setData`-after, inserted below drawn features via the same `firstUserLayer()` pattern `network-connectors.js` uses), colored by one data-driven `["match", ["get","cov"], …]` expression (`both` `#16a34a`, `one-side` `#f59e0b`, `none` `#dc2626`, `footway` `#2563eb` at a heavier line-width so mapped sidewalk geometry reads distinctly, `unknown` `#94a3b8` — map data symbols, exempt from the design-token rule per `CLAUDE.md` → "Design tokens and colors"). Hidden by default (`layout.visibility: "none"`) — this is an audit overlay the user opts into, not the walk network itself; it would otherwise visually fight `walk-network-line` on every load. Registered in `layers-panel.js` `REFERENCE` as "Sidewalk coverage", right after "Walk network" as its **own row** (not added to that row's `layers` array — different semantics, independent toggle). Called from `road-network.js`'s `updateUI()` behind a `typeof` guard, alongside the existing `App.refreshWalkNetworkLayer()` call — same single choke point for download/import/clear. Removes the source/layer entirely when no network is loaded, same convention as `refreshWalkNetworkLayer()`. **Pure (Phase 3):** `coverageStats(segments)` → `{ roadKm, footwayKm, crossingCount, byClass: {both, oneSide, none, unknown}, pctTagged, pctBoth }` from a plain segment array (the shape `App.getWalkNetworkSegments()` returns) — "road centerline" is any segment where `classifySidewalk(seg) !== "footway"`; `crossingCount` counts segments whose `footway === "crossing"` or non-empty `crossing` field; `pctTagged`/`pctBoth` are percentages of `roadKm` (`pctTagged` counts `both`+`one-side`+`none`, deliberately excluding `unknown`). Segment length is a turf-free equirectangular approximation matching `road-network.js`'s own snapping projection, so the pure block stays turf-free. Empty/null input → all zeros, never `NaN`. Golden-tested in `test/cases/walk-audit.mjs`. **App (Phase 3):** `App.getSidewalkCoverageSummary()` → `{ text, detail, warn }` or `null` when no network is loaded — mirrors `App.getConnectorReportSummary()` exactly (same one-line-footer pattern). `warn` fires when `pctTagged` is below 25% (the threshold below which sidewalk-only routing, if ever enabled, would be unreliable — see the plan's §1.4/Checkpoint 1), and `detail` names the caveat. Surfaced by both `walkshed.js` (`#wsCoverageReport`, right after `#wsConnReport`) and `transit-travelshed.js` (`coverageReportHTML()`, right after `connectionReportHTML()`) — both read the same global helper, no per-module state.

- **`connector-graph.js`** — Network Connectors pure planarization engine (`window.ConnectorGraph`, same engine-namespace convention as `window.Travelshed`/`window.TPI`). No turf/DOM/Map/App state — plain `[lng,lat]` coordinates and plain objects in/out so the golden harness loads it directly. `segmentIntersection(a,b,c,d)` (2D segment/segment intersection in local km space projected around `a`; `null` for parallel/collinear or an out-of-range hit), `pointToSegmentKm(p,a,b)` (nearest-point-on-segment, restates `road-network.js`'s `nearestOnSegmentKm` so this engine is self-contained), `splitChain(coords, splits)` (cuts a polyline at a list of `{segIndex, t, point}` records, sorting same-segment splits by `t`, dropping any resulting zero-length edge), and the top-level `planarizeConnectors(connectors, candidates, opts)` (`opts: {snapToleranceKm, weldVertices, splitCrossings}` → `{addEdges, removeSegIds, joins, orphans}`). Two-pass design: Pass A (crossing splits, only when `splitCrossings`) processes connectors in order against a pool that starts as `candidates` and grows with each finished connector's own edges, so a later connector can cross an earlier one too (`joins` records a connector-connector crossing under the *processing* connector's id, with `segId` set to the earlier connector's id); Pass B (welding, only when `weldVertices` and `snapToleranceKm > 0`) runs against the final pool so weld order among connectors doesn't matter. `pedBlocked` candidates are skipped in both passes — the bridge/freeway mitigation from `docs/network-connectors-plan.md` §1 — **except** a candidate that also carries `userExcluded: true` (`docs/sidewalk-data-plan.md` Phase 4): the guard is `pedBlocked && !userExcluded`, so a user-excluded street stays weldable/crossable (letting a connector recover walkability along it) while a real motorway/trunk never does. Golden-tested with a case pair for each pass (`planarize-crossing-userexcluded-joins`/`planarize-weld-userexcluded-joins` must join; `planarize-weld-pedblocked-still-rejected` and the pre-existing `planarize-pedblocked-exclusion` must not). A split or weld point that already coincides with an existing coordinate (within the `nodeKey` quantum, matching `road-network.js`'s 6-decimal quantization) reuses that coordinate rather than creating a split — the reused-node case still records a `"weld"` join but emits no extra edge. Re-splitting an already-split piece (the "double crossing" case) replaces its prior `addEdges` record rather than leaving a stale superseded edge behind. `road-network.js` supplies `candidates` (via its own spatial index) and applies the returned `addEdges`/`removeSegIds` to `_segmentIndex`/`_graph`; nothing in this file touches the live graph, `App.lines`, or any attribute. Golden-tested in `test/cases/connector-graph.mjs` (primitive checks for all three helpers, plus the 9 `planarizeConnectors` scenarios from the Phase 3 plan — mid-block crossing, double crossing, weld within/outside tolerance, `pedBlocked` exclusion, connector-connector crossing, exact-node reuse, collinear overlap, empty input — plus 3 more from `docs/sidewalk-data-plan.md` Phase 4 for the `userExcluded` carve-out). Wired into `road-network.js`'s `applyConnectorOverlay()` as of Phase 4 (welding) and Phase 5 (`splitCrossings: true` — mid-block crossing joins).

- **`travelshed.js`** — Transit Travelshed pure calculation engine (`window.Travelshed`, same engine-namespace convention as `window.TPI`). No turf/DOM/Map/App state — plain JSON in/out so the golden harness loads it directly. `parseHHMMtoMin`, `selectActiveBand` (wrap-aware), `initialWait`/`transferWait` (capped-initial/uncapped-transfer wait model — see `docs/transit-travelshed-plan.md` Appendix A), `rideMinAtDistance` (runTime-priority), `sampleStopPositions`, `propagateRide` (both/forward/loop-wrap), `bandNodeSets` (cumulative per-budget node sets), and the core `computeArrivalTimes` (layered-flood arrival-time propagation: initial boardings from an origin flood, egress-merge into a shared node-time map, one generalized transfer round). `computeArrivalTimes` takes three OPTIONAL walk-leg cap inputs in minutes — `accessMaxMin` (origin-flood seed + round-0 walk), `transferMaxMin` (round ≥1 walk), `egressMaxMin` (the egress-merge walk) — null/undefined = uncapped, backward compatible (see `docs/transit-travelshed-v2-walk-caps-plan.md` §2.2); it also returns `alightings: [{stopKey, alightMin}]`, the best (minimum) alighting time per stopKey across all rounds, consumed by the module's cluster-union polygonization (§2.4). Everything needing turf or the road graph lives in `road-network.js` or `js/projects/transit-travelshed.js`.

## API

### API — network-store.js
Road-network IndexedDB store — see the File Structure entry above for the record shape, the `save()`/`latest()` pruning and quota behavior, and the `_withStore()` transaction-activity rule.

`App.networkStore.supported()` → bool (false where IndexedDB is unavailable, e.g. some private-browsing modes; every caller degrades to "no cache", never to an error).

`App.networkStore.save(record)` → `Promise<boolean>`. Stores one network, then prunes oldest-first to `MAX_ENTRIES`. Never rejects.

`App.networkStore.latest()` → `Promise<record|null>`. The most recently stored network. Never rejects — returns null on any failure.

`App.networkStore.clear()` → `Promise<boolean>`. Empties the store. Called by `clearRoadNetwork()`.

`App.networkStore.MAX_ENTRIES` — 3. Each record is tens of MB and the realistic working set is "the area I'm analyzing now, plus the one before it".

### API — road-network.js
Offline routing engine (Overpass/file import → graph → Dijkstra). Public: `roadNetworkLoaded()` (bool), `roadNetworkEpoch()` (int, bumped on every network (re)build/clear — used by the walkshed cache to invalidate), `findLocalRoute(waypoints)`, `fetchRoadNetwork()`, `loadRoadNetworkFromFile(file)`, `exportRoadNetwork()`, `clearRoadNetwork()`, `clearRoadDownloadArea()` (removes only the downloaded-area outline, leaves the graph — wired to the Layers panel), `restoreCachedNetwork()` (async, `Promise<boolean>` — rebuilds from the IndexedDB copy of the last loaded network so a page refresh does not force another Overpass round trip; called once at startup from `app.js`, immediately after `App.cache.restore()`, so connectors and excluded ways are already registered and get re-applied by the rebuild it triggers. No-ops when a network is already loaded. **It deliberately routes through the same `rebuildNetwork()` → `updateUI()` path as a live download**, which is a correctness requirement rather than tidiness: the epoch bumps exactly once, so every epoch-keyed module cache (Walkshed, Transit Travelshed) invalidates precisely as it would after a fresh fetch and a restored network can never silently validate geometry a previous page load computed against it. The stored download extent is restored too, so `getRoadDownloadExtent()` — and Transit Travelshed's prompt-to-download coverage check built on it — keeps working with no re-download. A restored network under 48h old is reported like any other load; an older one adds "Re-download to refresh." to the same status line, since OSM street geometry does not meaningfully move in two days and nagging below that would be noise), and `computeWalkshed(lngLat, budgetKm, options)` → `{ polygon (turf Feature<Polygon|MultiPolygon>), reachableSegments (FeatureCollection of reachable street LineStrings), reachableCount, snap, computeMs, snapMs, floodMs } | null` (null when no network is loaded or the origin snaps > `SNAP_MAX_KM` (0.5 km) from the network). `computeWalkshed` runs a budget-limited flood Dijkstra (no `endKey` early-exit; prunes relaxations beyond `budgetKm`), collects settled nodes/edges, and builds the polygon via a concave-hull auto-relax loop (grow `maxEdge` until non-null → `turf.convex` fallback → small buffer for <3 nodes). **Multiple nested budgets (`docs/walkshed-bands-and-crossing-penalties-plan.md` Phase 2):** an optional `options.budgetsKm` — an ascending array of km values — floods once at `max(budgetsKm)` and thresholds the same `distMap` for each entry, adding `polygons: [{budgetKm, polygon, nodeCount}]` to the return (ascending, one entry per `budgetsKm` value — a degenerate/sparse band still gets an entry with `polygon: null`, never dropped) while `polygon`/`reachableSegments`/`reachableCount` keep meaning the LARGEST budget's values. Absent `options.budgetsKm` is byte-identical to pre-Phase-2 behavior — this is a hard backward-compat requirement, since `walkshed.js`'s `computeForPoint` and any other caller must keep working untouched until they opt in. `window.Travelshed.bandNodeSets` was considered and rejected as a way to build this: it takes a plain object keyed by node, while `distMap` is a `Map` with tens of thousands of entries, so converting would cost more than the inline threshold loop. **Class-aware traversal:** the shared network is tagged per-edge/segment with `pedBlocked`/`carBlocked` in `buildGraph()`, derived from the OSM `highway` class and `foot` tag via `isPedForbidden(hwy, foot)` / `isCarForbidden(hwy)` (`PED_FORBIDDEN_HWY` = motorway/trunk + their `_link` ramps; `CAR_FORBIDDEN_HWY` = footway/path/steps/pedestrian/cycleway; an explicit `foot=yes/designated/permissive` or `foot=no` overrides the class default). **User-excluded streets (`docs/sidewalk-data-plan.md` Phase 4):** `buildGraph()` also ORs a private `_excludedWays` Set (hydrated only via `App.setExcludedWays(ids)` below) into `pedBlocked`, and records the result separately as `userExcluded` on the segment — the flood therefore skips a user-excluded street exactly like a class-blocked one, but `getWalkNetworkSegments()`/`connector-graph.js` can still tell the two apart. `carBlocked` is untouched, so `findLocalRoute` (driving) never sees an exclusion. The walkshed flood and its reachable-streets layer skip `pedBlocked` edges (freeways excluded), the driving `dijkstra` skips `carBlocked` edges (never routes over pedestrian-only ways), and `snapToNetwork(lngLat, mode)` skips segments this mode can't use via a per-candidate `pedBlocked`/`carBlocked` check (`"walk"` from `computeWalkshed`, `"drive"` from `findLocalRoute`; absent mode = no filter). One download, two interpretations. **Snap acceleration:** `snapToNetwork` queries a uniform spatial grid (`_segGrid`, built by `buildSegGrid()` alongside `_segmentIndex` in `buildGraph()`, cell size ≈0.5 km sized from the network bbox's mid-latitude) instead of scanning every segment — only the 3×3 cell neighborhood around the query point (~1.5 km²) is checked, which always covers the `SNAP_MAX_KM` rejection radius. Candidate segments are compared with inline equirectangular point-to-segment math (`nearestOnSegmentKm`, projected around the query point) instead of per-segment `turf.lineString`/`turf.nearestPointOnLine` allocations — on a city-scale Overpass download (tens of thousands of segments once footways/paths are included) the old whole-network scan cost 1-3 seconds per call and was the actual bottleneck behind "Walking from stop x/y" in Transit Travelshed, not the flood itself. `_segGrid` is cleared in `clearRoadNetwork()` alongside the rest of the graph state. Graph weights are in **km**, so `budgetKm = walkSpeedKmh * (minutes / 60)` (the Walkshed module's UI/attributes are in **mph**; it converts to km/h before calling `computeWalkshed`). **`fetchRoadNetwork()`** downloads Overpass roads for the current map view **expanded ×1.5 on each side** (`turf.transformScale`, area ≈ 2.25×) so edge routes/walksheds aren't starved of streets; the query pulls vehicle roads **and** pedestrian-specific ways (`living_street|pedestrian|footway|path|steps|cycleway`) and captures the `foot` tag, so walksheds follow real walking connections while drive-routing ignores the pedestrian-only classes (see class-aware traversal above); it warns via `window.confirm` when the expanded area exceeds `MAX_AREA_WARN_KM2` (~2000 km², since Overpass file size can't be known up front), and records the fetched extent as `_downloadedBboxPolygon`. A subtle dashed fuchsia (`#c026d3`) rectangle outline (`road-dl-area` source / `road-dl-area-line` layer, styled like the Municipal Boundaries border) is drawn/updated/removed through `updateUI()` (the single choke point for download / import / clear). File-imported networks draw no outline (no known download area); `clearRoadNetwork()` and `clearRoadDownloadArea()` remove it. The outline is listed in the Layers panel `REFERENCE` band as "Road download area." **Transit Travelshed primitives** (added alongside `computeWalkshed`, sharing its private `_graph`/`runWalkFlood`): `computeWalkCostMap(lngLat, budgetKm)` → `{ distMap: Map<nodeKey, distKm>, snap, accessNodes: [{nodeKey, extraKm} × 2], computeMs, snapMs, floodMs } | null` — the same budget-limited flood as `computeWalkshed` but returns the raw per-node cost map instead of a polygon, plus the two straight-line "access" bridges (snap coord → each bracketing segment endpoint) a caller needs to compute walk time to that exact stop from any other cost map without an O(nodes) turf scan. `polygonizeNodeSet(coords, maxEdgeKm)` — exposes the same concave-hull-with-auto-relax polygonizer `computeWalkshed` uses, for building band isochrones from an arbitrary node-coordinate list. `nodeKeyToCoord(key)` — alias for the internal `keyToCoord`. `snapWalk(lngLat)` — alias for `snapToNetwork(lngLat, "walk")`. `getRoadDownloadExtent()` → `Feature<Polygon> | null`, the last Overpass download's recorded extent (same value that drives the dashed outline). `fetchRoadNetworkForExtent(extentPolygon)` → `Promise<boolean>` — downloads roads for a **caller-supplied** extent instead of the current map view (built on the same `fetchNetworkForBounds` helper `fetchRoadNetwork()` uses); replaces the loaded network wholesale and bumps `_networkEpoch`, so every module cache keyed by epoch (Walkshed, Travelshed) invalidates automatically. **Atomicity note:** `computeWalkCostMap`/`computeWalkshed` are synchronous and atomic — the temp snap-node injection, flood, and cleanup all happen inside one call (cleanup in a `finally`). Callers may `await`-yield BETWEEN calls, never during; the temp-node graph mutation is not async-safe. **`getWalkNetworkSegments()`** → plain array (not a turf FeatureCollection) of `{ coords: [[lng,lat],[lng,lat]], kind: "base"|"connector", sidewalk, footway, hwy, wayId, excluded, name }` for every `_segmentIndex` entry where `pedBlocked` is false **or** `userExcluded` is true (`docs/sidewalk-data-plan.md` Phase 4 — a user-excluded segment must stay visible/clickable, unlike a class-blocked one, which is still skipped). `sidewalk`/`footway`/`hwy`/`name` default to `""` and `wayId` to `null` on a connector-derived segment or a legacy import (Phase 1 — additive fields, existing consumers ignore them); `excluded` mirrors the segment's `userExcluded` flag. Cached keyed on `_networkEpoch` (a city network has tens of thousands of segments and this is called on every layer refresh) — repeat calls with an unchanged epoch return the identical array reference. Consumed by `network-connectors.js`'s "Walk network" reference layer; see `docs/network-connectors-plan.md`. **`setNetworkConnectors(connectors, opts)`** (`docs/network-connectors-plan.md` Phase 4) — the Network Connectors adapter, called only by `network-connectors.js`. Stores plain `connectors: [{id, coords}]` + `opts: {snapToleranceKm}` and runs `rebuildNetwork()` (`buildGraph(_roadGeoJSON)` → `applyConnectorOverlay()` → one `_networkEpoch++`), so a connector change invalidates every epoch-keyed cache (Walkshed, Travelshed) exactly once, same as a network reload. `applyConnectorOverlay()` queries `_segGrid` for candidate base segments near the connectors, calls `window.ConnectorGraph.planarizeConnectors(...)` (welding only — `splitCrossings: false` — until Phase 5), removes each replaced base segment's two directed graph edges, and adds the returned edges with `pedBlocked: false, carBlocked: true` (walk-only; never affects `findLocalRoute`), rebuilding `_segGrid` wholesale afterward. Returns the overlay report: `{ reason: "no-base-network" }` when `_roadGeoJSON` is null, else `{ addEdges, removeSegIds, joins, orphans }` (counts plus the raw `ConnectorGraph` join/orphan records). `_connectors`/`_connectorOpts` persist across a base-network reload (a fresh Overpass download or file import), so `rebuildNetwork()` re-applies the same overlay automatically — connectors are never merged into `_roadGeoJSON` itself. **`setExcludedWays(ids)`** (`docs/sidewalk-data-plan.md` Phase 4) — the ONLY sanctioned write path to the private `_excludedWays` Set that `buildGraph()` reads: stores `new Set(ids)`, writes `ids` back to `App.networkSettings.excludedWayIds` (round-trips through the session cache), saves, then `rebuildNetwork()` — so an exclusion re-applies automatically after a re-download (way ids are stable) and the epoch bumps exactly once per change, mirroring `setNetworkConnectors()` exactly. **Weld carve-out:** `collectCandidateSegments()` now also passes `userExcluded` on each candidate object, so `connector-graph.js`'s `pedBlocked` weld/crossing-split guards (changed to `pedBlocked && !userExcluded`) let a connector drawn along a user-excluded street still join it, while a real motorway/trunk (`pedBlocked` without `userExcluded`) still never welds — see that file's entry and the plan's §1.5 "exclude coarsely, restore precisely". **Crossing penalties (`docs/walkshed-bands-and-crossing-penalties-plan.md` Phase 5, off by default):** every graph edge and `_segmentIndex` entry now carries the source way's OSM `highway` class as `hwy` (`""` for connector-derived edges, treated as minor). `buildNodeTierMap(graph)` walks the graph once — a node's own adjacency-list length equals its incident-segment count, exactly what `window.WalkCost.nodeTier()` needs — building `_nodeTier: Map<nodeKey, "major"|"minor">` (nodes earning no penalty are omitted, not stored as null); it's recomputed both in `buildGraph()` and at the end of `applyConnectorOverlay()`, so it stays in sync with connector-driven intersection changes and is cleared in `clearRoadNetwork()`. `floodDijkstra(startKey, budgetKm, penaltyKm)` takes an optional third `{major, minor}` km-value object and adds the relevant tier's penalty to `newDist` when arriving at a `_nodeTier`-tagged node, before the budget-prune check — so an over-budget crossing still correctly prunes. `runWalkFlood(lngLat, budgetKm, opts)` threads `opts.crossingPenaltyKm` down to `floodDijkstra`; `computeWalkshed(lngLat, budgetKm, options)` passes `options.crossingPenaltyKm` through the same way. `computeWalkCostMap` deliberately never passes a penalty (Transit Travelshed is its only consumer and is out of scope for this phase — a documented, deliberate follow-up), so its output is bit-identical. Absent/zero penalty values are byte-identical to pre-Phase-5 output — verified pixel-identical at 0 s before shipping.

### API — network-connectors.js
`App.refreshWalkNetworkLayer()` — rebuilds the discreet "Walk network" reference layer (source `walk-network` / layer `walk-network-line`) from `App.getWalkNetworkSegments()`; removes the source/layer entirely when no network is loaded. Called from `road-network.js`'s `updateUI()` (every download/import/clear) and from `refreshNetworkConnectors()` below (every overlay rebuild). Styled discreetly (`#94a3b8`, width 1, opacity 0.45) and inserted below the first drawn-feature layer present (same `firstUserLayer()` pattern as `gtfs.js`). This was Phase 1 of `docs/network-connectors-plan.md`.

**Phase 4 (`docs/network-connectors-plan.md`):** `App.networkSettings` — `{ snapToleranceFt: 50, crossingMajorSec: 0, crossingMinorSec: 0, excludedWayIds: [] }` (the two crossing fields added in `docs/walkshed-bands-and-crossing-penalties-plan.md` Phase 5, `excludedWayIds` added in `docs/sidewalk-data-plan.md` Phase 4 — all defaulting to 0/off/empty and backfilled defensively on an already-created object so an older page load never leaves them `undefined`), global values read/written by both the Walkshed and Transit Travelshed Advanced blocks (never per-module state — see the plan's §2 "Known conflict"); persisted as additive `networkSnapToleranceFt`/`networkCrossingMajorSec`/`networkCrossingMinorSec`/`networkExcludedWayIds` session-cache fields (`cache.js`). `excludedWayIds` is written ONLY through `App.setExcludedWays(ids)` (`road-network.js`) — see that entry — never poked directly, since road-network.js hydrates it into a private `Set` that `buildGraph()` actually reads. `App.refreshNetworkConnectors()` — scans `App.lines` for `attributes.networkRole === "connector"` Lines (`collectConnectorLines()`, skipping hidden features, returning plain `{id: "line:"+idx, coords}`), computes a cheap `JSON.stringify`-based signature from the collected geometries + tolerance, and no-ops if unchanged; otherwise converts the tolerance to km (`ft * 0.0003048`), calls `App.setNetworkConnectors(connectors, {snapToleranceKm})`, caches the returned report, and refreshes the walk-network layer. The signature guard is what makes it safe to call from every relevant site with no debouncing: `App.notifyProject()` (`app.js`), a line vertex's drag-**end** commit (`editing.js`, not per-frame), the `networkRole` field's `onChange` (`feature-attributes.js`'s Phase 2 `onNetworkRoleChange` stub), and both modules' snap-tolerance inputs on `change`. `App.getConnectorReport()` returns the last cached report (`{addEdges, removeSegIds, joins, orphans}` or `{reason: "no-base-network"}`). As of Phase 5, `road-network.js` planarizes with `splitCrossings: true`, so a connector drawn straight across a street joins it mid-block, not only at a welded endpoint.

**Phase 6:** a `network-joins`/`network-joins-point` circle layer renders every `joins` entry (`"crossing"`/`"weld"`, small filled muted dot) and every `orphans` entry (a larger hollow amber-stroked circle, so a dangling connector end is findable at a glance) via one data-driven `["match", ["get","kind"], ...]` paint expression — not three layers. Built by `refreshJoinMarkers()`, called from the end of `refreshWalkNetworkLayer()` so both layers stay in lockstep from the single `walk-network-line` Layers-panel row (see `layers-panel.js` below); `refreshWalkNetworkLayer()` also re-syncs its cached report from `App.getLastConnectorOverlayReport()` (a raw `road-network.js` accessor, distinct from `App.getConnectorReport()`) at the top of every call, since a plain base-network reload re-runs `applyConnectorOverlay()` via `rebuildNetwork()` without going through `App.setNetworkConnectors()` — without that re-sync the marker layer would go stale after a fresh Overpass download even though the join/orphan geometry changed. `App.getConnectorReportSummary()` — `{ text, detail, warn }` or `null` when no connectors exist — builds the Walkshed/Transit Travelshed results-footer line (`"N walk connectors · M joins · K ends not connected"`, plus, when `warn` is true, a `detail` line naming the worst-off orphan by its Line name and nearest-street distance in feet, via the module-local `getConnectorLineName(connectorId)` resolver that parses the `"line:"+idx` convention back to `App.lines[idx].properties.name`).

**Phase 4 (`docs/sidewalk-data-plan.md`) — manual street exclusion:** an excluded segment is NOT styled with a data-driven `line-dasharray` on `walk-network-line` itself — MapLibre GL JS's `line-dasharray` only supports a static array or a zoom function, never a per-feature expression; a `["case", ...]` there fails style validation and `map.addLayer` silently refuses to add the layer (no thrown error, just a console warning) — which took the whole base layer down the first time this was tried (nothing rendered, nothing was clickable, even though the unrelated sidewalk-coverage layer worked fine). The correct fix is a second layer, **`walk-network-excluded-line`** (`WN_EXCLUDED_LAYER`), same source, `filter: ["==", ["get","excluded"], true]` (a `filter`, unlike a paint property, CAN vary per feature), painted red/dashed/wider/more-opaque and stacked above the base layer — `filter` narrows *which* features a layer sees; `line-dasharray` still only ever gets one static value per layer. A third layer, **`walk-network-hover-line`** (`WN_HOVER_LAYER`), renders a filtered highlight (`["==", ["get","wayId"], <hovered wayId>]`, amber, width 5) over the SAME source — a way is usually many coordinate-pair segments, so this is the only way to light up an entire way on hover rather than just the segment under the cursor (the plan's §2 "hover must preview the whole way before a click commits it"). `wireWalkNetworkInteraction(map)` is called exactly once, right after all three layers are first created (MapLibre listeners on a layer id persist across `setData()`, so re-wiring on every `refreshWalkNetworkLayer()` call would stack duplicate handlers): `mousemove` sets the hover filter and shows a `maplibregl.Popup` naming the street (`properties.name`, defaulting to "Unnamed street"), its length in feet (summed via `turf.length` over every feature sharing that `wayId` — `wayFeatures(wayId)`/`wayLengthFt(wayId)`), its current state (Walkable/Excluded), and what a click will do; `mouseleave` clears both; `click` calls `toggleExcludedWay(wayId)`, which flips membership in `App.networkSettings.excludedWayIds` and calls `App.setExcludedWays()` — the only write path. A segment with `wayId: null` (a legacy pre-Phase-1 import) is guarded out of hover/highlight entirely and its click sets a one-line status message instead of throwing. **`App.setExcludedWays(ids)` calls `updateUI()`, not just `rebuildNetwork()`** — the second bug found alongside the dasharray one: `rebuildNetwork()` alone updates the internal graph/`_segmentIndex` but never refreshes the `walk-network` map source, so an exclusion changed routing behavior but never visibly changed anything on the map until some unrelated event happened to refresh the layer. `updateUI()` is the same choke point `fetchNetworkForBounds`/`loadRoadNetworkFromFile` already call after rebuilding, and it in turn calls both `App.refreshWalkNetworkLayer()` and `App.refreshSidewalkCoverageLayer()`. All three layers are registered under the single "Walk network" `layers-panel.js` row (`walk-network-line`, `walk-network-excluded-line`, `network-joins-point` all toggle opacity together; `walk-network-hover-line` is a pure interaction layer and deliberately has no Layers-panel row of its own).
