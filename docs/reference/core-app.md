# Core app

Reference detail moved verbatim from `CLAUDE.md`. Read the code when this and the code disagree.

## Files

- **`index.html`** — App shell: grouped toolbar, map, feature/layers panel, floating module-panel container, dormant hidden sidebar markup, script tags

- **`style.css`** — Core layout, toolbar, feature panel, module popup, floating widgets, basemap switcher, BAS styles (.bas- prefix), TPI styles, RF styles (.rf- prefix), FTA styles (.fta- prefix), TVI styles (.tvi- prefix), pill rating colors

- **`sidebar-v2.css`** — Dormant legacy sidebar styles (scoped under hidden #sidebar); retained for compatibility

- **`app.js`** — Startup, module registry, event wiring. Variable checkbox UI is built at runtime by buffer-summary.js from VAR_META in utils.js (no sidebar Data Inputs panel).

- **`config.js`** — Third-party API keys (`App.CARTO_API_KEY`, `App.CENSUS_API_KEY`) + a `localStorage` per-browser CARTO override (`mat-carto-key`). Loads FIRST, before utils.js. **Everything in this file is public** — static site, no build step, public repo, GitHub Pages: values here are served verbatim to the browser and cannot be hidden. Only ever put public, rate-limited, read-only credentials here. See `docs/carto-api-key-plan.md`.

- **`utils.js`** — Stable per-type feature IDs (`nextFeatureId`, `ensureFeatureIds`) and ID-based feature refs (`featureRef`, `resolveFeatureRef`, `featureById`, plus the `"type:<id>"` key helpers `featureRefKey` / `parseFeatureRefKey` and the legacy-session migrators `migrateIndexRefKey` / `indexFilterToRefs` / `uncheckedRefsFromIndexFilter`), CSV parsing, number formatting, GEOID normalization, VAR_META (single source of truth — label, category, group, displayInChecklist, denominator), GROUP_INFO, getCheckboxGroups, getDenominator, getSelectedVars, the feature-usage hook (`registerFeatureUsage` / `describeFeatureUsage`, see the utils.js API)

- **`sidebar.js`** — Dormant legacy sidebar manager: addPanel, removePanel, toggle, render. `#sidebar-wrap` ships hidden and `App.sidebar.render()` is not called; current Data/Analysis entry points are toolbar menus and module popups.

- **`map.js`** — MapLibre GL map instance, basemap registry + switcher control, cursor management. CARTO basemaps require `App.CARTO_API_KEY` (appended as `?key=` to every `basemaps.cartocdn.com` tile URL once at init, so the initial style and `switchBasemap()` both read already-keyed URLs). With no key the three CARTO entries are filtered out of `BASEMAPS` and the default falls back to `esri-light-gray`, so a fork / exhausted quota / domain-locked local dev never renders a watermarked map.

- **`census.js`** — TIGERweb geometry queries, ACS data fetch, area-weighted aggregation, per-geography overlap fractions (`computeGeoOverlapFractions`)

- **`lodes.js`** — LODES .csv.gz download/upload/parse, block-level employment

- **`cache.js`** — Session cache: save/restore/reset via localStorage; JSON import/export

- **`popup.js`** — Analysis popup manager: open/close module popups, adaptive panel widths, title-bar dragging locked below the browser top with release-time left/right/bottom recovery, collapse/expand anchored on the caret/close controls, and floating map widgets (legend)

- **`module-buffers.js`** — Shared analysis-buffer helper: `App.ANALYSIS_BUFFER_DEFAULT_MILES` (0.5) / `_MIN_MILES` (0.05) / `_MAX_MILES` (5), `foldAnalysisUnion`, `buildAnalysisBuffer`, `buildDisplayBufferSet`, `readAnalysisBufferMiles`, `buildAnalysisBufferSet`. Lets Feature Area Analysis, Transit Coverage, Transit Propensity, Ridership Forecasting, and Corridor Scoring choose either a module-owned analysis distance or the selected current Feature Settings buffers without changing map state — see those modules' entries below and `docs/module-buffer-distance-plan.md`.

- **`analysis-checklist.js`** — Shared hidden-feature helpers for analysis checklists (`docs/hidden-features-analysis-plan.md` Phase 1). `App.decorateHiddenRow(rowEl, checkboxEl, feature, includeHidden)` (disables the box, adds `.ac-hidden` + a `.ac-hidden-tag` "hidden" tag + tooltip for a hidden feature unless `includeHidden`; never changes `checkboxEl.checked`), `App.buildIncludeHiddenToggle({id, checked, onChange})` (inline checkbox + label for beside Select all | Clear), `App.hiddenSelectionMessage(hiddenCount)` -> `{error, notes}` (standard wording). Also `App.hiddenSignature(refs)` (stable string of which `{type,id}` refs are hidden — modules snapshot it at run time and compare in `update()` to mark results stale) and `App.featureGeomSignature`. Loads right after `module-buffers.js`. Adopted by Feature Area Analysis, Transit Propensity, Corridor Scoring, Transit Coverage and Ridership Forecasting: hidden rows are disabled+tagged (their saved checked state is never touched), an Include hidden toggle sits beside Select all | Clear, results notes say "Includes N feature(s) hidden on the map.", and a hide/show or toggle change after a run shows the stale banner. Each module saves its toggle as an additive cache field, default `false`, no schema bump: `includeHidden` (Feature Area Analysis, Transit Propensity, Corridor Scoring, Transit Coverage — one toggle for both its lists) and `includeHiddenCalib` / `includeHiddenDemand` (Ridership Forecasting, one per checklist). Audit-only (no change): Title VI, Walkshed and Transit Travelshed — see the plan's Phase 4 findings.

- **`choropleth.js`** — Shared choropleth rendering engine (`App.choropleth`); consumers are Feature Area Analysis (first, Phase 1-2) and, as of Phase 3, TPI (`id: "tpi"`), Ridership Forecasting (`id: "rf"`), and Corridor Scoring (color-expression logic only, still a line layer) — see `docs/feature-area-choropleth-plan.md`. Pure, golden-testable classification math — `computeClassBreaks` (quantile/equal, `nClasses-1` inner breaks, dedup on heavily tied data, degenerate all-equal/single-value/empty cases), `buildStepColorExpr` (MapLibre `step` paint expression wrapped so non-numeric/missing renders a no-data color instead of the first class), `buildInterpolateColorExpr` (MapLibre `interpolate`/`linear` gradient expression across a ramp's 5 colors evenly spaced from `min` to `max`, same no-data guard; a degenerate range — no data, or `min === max` — falls back to a single solid color instead of the 2-point gradient MapLibre would reject for non-ascending stops), `formatBreakLabels` — plus a map-facing instance API keyed by an `id` string so multiple modules can each own one live choropleth without colliding: `render(opts)` (creates/updates source `"<id>-choropleth"` + layers `"<id>-choropleth-fill"`/`"-line"`, same create-once/setData-after + hover-popup pattern as TPI's original inline version; `opts.method: "continuous"` (Phase 3 Step 3.1) switches from classed breaks to `buildInterpolateColorExpr`, returning `breaks: []` and a `colors` array matching what was actually painted — the full 5-color ramp for a real range, 1 solid color when degenerate, `[]` when there's no data at all, so a caller's legend never shows more swatches than colors actually drawn; returns `{breaks, colors, nEffective, min, max}` for the caller's legend), `remove(id)` (idempotent), `setVisible(id, bool)`, and `fillLegend(containerEl, opts)` for the generic legend fragment below. `RAMPS` holds the curated ColorBrewer presets (`blues` default, `heat`, `greens`, `rdbu`).

- **`present-overlays.js`** — Presentation mode overlay manager: draggable/resizable legend, north arrow, and title. Registers `"present-overlays"` cache state and listens for `mat:present-mode-change` from `App.setPresentMode()` in `app.js`. Legend auto-sizes to row content with balanced horizontal padding until manually resized. Title auto-sizes to entered text until manually resized; manual title size persists and title text scales from box width.

- **`choropleth-legend.html`** — Generic choropleth legend fragment shared by `App.choropleth`'s map-facing API (`docs/feature-area-choropleth-plan.md`): a `.tpi-legend-panel`-style shell with a `.cl-legend-title` line, 5 pre-built `.cl-legend-row` rows (each a `.cl-legend-swatch` + `.cl-legend-label`, unused rows hidden by `fillLegend`), and a `.cl-legend-note` line. Filled after the floating widget mounts via `App.choropleth.fillLegend(containerEl, {title, labels, colors, note})` — the same fill-after-mount pattern as `transit-travelshed-legend.html`. First consumer is Feature Area Analysis (widget id `"bas-legend"`).

## API

### API — utils.js
`setStatus(s)`, `parseCSV(text)`, `fillSelect(el, opts, placeholder)`, `enableSelect(el, bool)`, `toNumberSafe(v)`, `normalizeTractGEOID(raw)`, `guessHeader(headers, candidates)`, `VAR_META`, `GROUP_INFO`, `getMeta(code)`, `getCheckboxGroups()`, `getCheckboxGroupMembers(groupKey)`, `getDenominator(code)`, `setAggUI(meta)`, `formatValue(val, meta)`, `getSelectedVars()`, `mapToObj(map)`, `objToMap(obj)`, `nestedMapToObj(outerMap)`, `nestedObjToMap(obj)`, `FEATURE_COLORS`, `POLYGON_DEFAULT_COLOR`, `sectionColors`, `resolveFeatureColor(featureType, feature)`, `_nextColorSeq()`, `_advanceColorSeqPast(n)`, `FEATURE_ID_PROP`, `nextFeatureId(type)`, `ensureFeatureIds()`, `_assignFeatureIds(arraysByType)`, line-style helpers `LINE_STYLES` / `LINE_STYLE_LAYERS` (`{line: [3 ids], route: [3 ids]}`) / `LINE_STYLE_DASH` / `normalizeLineStyle(v)` / `lineStyleFilter(style)` / `lineStyleLayerIds(type?)` / `lineStyleLayerType(layerId)` / `addLineStyleLayers(map, type, sourceId, paint)`, and `APPEARANCE_OVERRIDE_KEYS` / `copyAppearanceOverrides(srcProps, dstProps)` (used by every `duplicateX`; `_offset`/`_offsetManual` are copied only when the offset is manual — an automatic overlap offset is recomputed for the copy)

**Stable feature IDs** (`docs/feature-merge-plan.md` Phase 1): every drawn feature has a unique integer ID per type in `properties.pointIdx` / `lineIdx` / `routeIdx` / `polyIdx` (`App.FEATURE_ID_PROP = { point, line, route, polygon }` maps type → property name). The IDs map a clicked map feature back to its array index (`editing.js findXIndex*`) and link stops to routes (`attributes.associatedRoutes[].featureId`, read by Transit Travelshed and the route picker). **Always get a new ID from `App.nextFeatureId(type)`** — a monotonic per-type counter, never reuse or derive from `array.length + 1` (that repeats after a delete). Default display names ("Route 3") are independent of the ID. `App._assignFeatureIds(arraysByType)` is the pure (golden-tested, `test/cases/feature-ids.mjs`) repair pass: it stamps a fresh ID on any feature whose ID is missing, not a positive integer, or duplicates an earlier feature of the same type (the first/older one keeps it) and returns `{ changes: [{type, index, oldId, newId}], maxByType }`. `App.ensureFeatureIds()` runs it over the live arrays and advances the counters past every ID in use; `cache.js applyState()` calls it after pushing features, so session restore, file import, shapefile/CSV/GeoJSON import and undo/redo are all covered (idempotent — already-unique IDs are never renumbered, so no schema bump). The counters themselves are saved as the additive `featureIdCounters` session field (`App.getFeatureIdCounters()` / `App.advanceFeatureIdCounters(stored)`, which only ever raises them), so an ID that belonged to a deleted feature is not reissued after a page reload. A stop link that referenced a duplicated ID keeps pointing at the first (older) feature. Any new code path that pushes a feature straight into `App.points/lines/routes/polygons` must stamp its ID with `nextFeatureId`. **Module references by stable ID** (Phase 4b): array indices shift on every delete/merge, so a module must never remember a feature by index. Store a ref `{ type, id }` (`App.featureRef(type, index)` → `{type, id}` | `null`) and resolve it at USE time with `App.resolveFeatureRef(ref)` → current index or `-1` (`App.featureById(type, id)` → feature | `null`); never cache the resolved index. A `-1`/`null` means the feature was deleted or merged away — show it as missing and skip/refuse, never fall back to another feature. The pure cores `App._featureRefIn(arraysByType, type, index)` / `App._resolveRefIn(arraysByType, ref)` are golden-tested (`test/cases/feature-refs.mjs`). **Legacy-session migration:** `cache.applyState` pushes the features in their saved order (and runs `ensureFeatureIds`) BEFORE any module `apply()` hook, so inside `apply()` a legacy saved array index still points at the right feature — convert index refs to ID refs right there (not later), idempotently (leave ID-form data alone), and turn an index that no longer resolves into a missing ref rather than guessing. Done for Route Costing / Trip Builder (service keys) and Title VI; the analysis modules listed in `docs/feature-merge-plan.md` 4b part 2 (TPI, Ridership Forecasting, Corridor Scoring, Transit Coverage, Feature Area Analysis) still store indices. Run-time index arrays rebuilt from checkboxes at run time may stay as indices. Browser smoke test: `NODE_PATH=<playwright>/node_modules node test/feature-merge-smoke.mjs` (see `test/ui-screens/capture.mjs` for the Playwright setup; later merge phases append assertions).

**Feature usage hook** (`docs/feature-split-plan.md` Phase 3; in utils.js because it is the first App file, so every module can register at load time and merge.js/split.js can consume it): `App.registerFeatureUsage(fn, {module, severity})` — `fn(type, id)` returns labels (strings, or `{label, severity}`) describing how the module refers to that feature; `App.describeFeatureUsage(type, id)` → `[{module, label, severity: "warn"|"info"}]`, each provider wrapped in try/catch (a throwing provider is skipped). Providers read module closure state only (safe before the popup is ever opened). Registered: **Title VI** (warn — `"Title VI · <scenario> · 'before'|'after' of <adjustment>"` for every alteration ref), **Ridership Forecasting** (warn — calibration CSV match rows by `featureId`, which match by name; info — the selected corridor), **Corridor Scoring** (info — ranked in the last results), **Transit Propensity** (info — selected corridor, or in the last results' `bufferByRef`), **Route Costing** (info — pattern of a multi-pattern Service, or costed in the last results; via `App.buildTransitServices`), **Trip Builder** (info — generated trips stored for the feature's Service). Shown by the Split and Merge dialogs; a new module that remembers features should register one.

`VAR_META` is the single source of truth for variable metadata. Per-entry fields: `source` ("ACS"|"LODES"), `agg` ("sum"|"avg"|"ratio"), `fmt`, `label`, `category`, optional `codes` (multi-code derived sums), optional `tractOnly`, `numerator`/`denominator`/`ratioLabel` (ratio aggregations only). Checkbox-UI fields (drive the popup): `displayInChecklist: true` for individual checkboxes, `group: "GROUP_X"` for group members, `denominator: "<code>"` or `"$group"` for the percent column. `GROUP_INFO` holds display labels for `GROUP_*` keys. `getCheckboxGroups()` returns `{ groupKey: [memberCodes] }` derived from `VAR_META`. `getDenominator(code)` returns `{ type: "var", code }` | `{ type: "group", codes }` | `null` (returns `null` for ratio aggregations).

**Feature color cascade** (one resolver for every drawn feature type, resolved fresh on every render — points, lines, routes, and polygons all follow it identically): `resolveFeatureColor(featureType, feature)` returns, in order, (1) `feature.properties.color` when non-empty — a per-feature override; (2) `App.sectionColors[featureType]` when non-empty — a flat type-level default set from the Layers tab; (3) **Automatic** (`sectionColors[featureType] === null`) — for `line`/`route`, `FEATURE_COLORS[feature.properties.colorSeq % FEATURE_COLORS.length]`, so each feature keeps a stable, distinct palette color; for `point`/`polygon`/`label`, a fixed built-in color (there is no rainbow mode for those types). `properties.color` is therefore an override, not a value — empty string (or absent) means "inherit," exactly like the opacity/weight/buffer/offset overrides elsewhere in the appearance cascade. `colorSeq` is a monotonic integer stamped once at creation (`_nextColorSeq()`) so a line/route's palette slot survives later deletions elsewhere in the array (an array-position lookup would recolor later features whenever an earlier one is removed); `_advanceColorSeqPast(n)` is called on session restore so a freshly drawn feature never collides with a `colorSeq` already stamped on a restored one. A feature with no stamped `colorSeq` (none exist post-migration, see `cache.js`'s v4 migration below) falls back to its live array position, reproducing the exact color it already had. `App.sectionColors` (`{ point, line, route, polygon, label }`, each `null` = Automatic or a hex string) is persisted by `cache.js` across reload/export/import. `js/core/features.js`'s `getTypeDefaultColor(type)` delegates to this same cascade for the "no specific feature to resolve a palette slot for" case (used by style previews, color-picker seeds, and every `properties.color || getTypeDefaultColor(type)` reader). See `docs/feature-color-system-plan.md` for the full design rationale. **Last action wins** (`docs/feature-color-sync-plan.md`): a type-wide color set in the Layers tab (or its × reset to Automatic) goes through `App.setTypeColor(type, color|null)` (features.js), which pushes one undo snapshot, sets `sectionColors[type]`, **clears `properties.color` on every feature of that type** (`App.clearFeatureColorOverrides`), re-renders and refreshes the Features pane, Layers pane and Attributes pop-up swatch; a per-feature color set afterwards (`App.updateFeatureColor`) wins for that feature until the next Layers change. **Every swatch/icon that represents a specific feature must use `App.resolveFeatureColor(type, feature)`** — never `properties.color || getTypeDefaultColor(type)`, which ignores a line/route's rainbow slot (`getTypeDefaultColor` is only for contexts with no specific feature). The Layers Style defaults preview for Lines/Routes draws a rainbow gradient while the type is Automatic. Browser smoke test: `test/feature-color-smoke.mjs`.

### API — map.js
`map` (MapLibre instance), `switchBasemap(basemapId)`, `getBasemaps()` (returns `[{id, name}]`), `getCurrentBasemapId()`, `getThemeBasemapId(isDark)`

Basemap IDs: `"carto-light"` (default), `"carto-dark"`, `"carto-voyager"`, `"osm"`, `"satellite"`, `"esri-dark-gray"`, `"esri-light-gray"` (the last two are Esri Canvas raster basemaps — muted background, streets emphasized, minimal labels)

**CARTO key + keyless fallback.** CARTO requires an API key on `basemaps.cartocdn.com` (unkeyed tiles are stamped "API KEY REQUIRED"). `App.CARTO_API_KEY` comes from `js/core/config.js` and is applied once at init to every CARTO tile URL, so both consumers — the initial style and `switchBasemap()` — read already-keyed URLs. Note those are **separate code paths**: the initial style is built directly from the registry, not via `switchBasemap`, so a key applied in only one place leaves the default basemap broken on load. When the key is empty the three CARTO entries are removed from `BASEMAPS` and the default becomes `"esri-light-gray"`; that is a supported state (fork, exhausted quota, or domain-locked local dev), not an error.

**`getThemeBasemapId(isDark)`** returns the light/dark basemap for the active family — CARTO when keyed, Esri Canvas when not. Dark-mode callers in `app.js` **must** use it rather than hardcoding `"carto-light"`/`"carto-dark"`: those ids do not exist in the keyless path and `switchBasemap` silently returns on an unknown id, which would strand the map on the wrong-theme basemap.

CARTO and OpenStreetMap attribution must stay visible on the CARTO basemaps — it is a license condition of the free tier.

### API — cache.js
`cache.save()`, `cache.restore()`, `cache.reset()`, `cache.exportToFile()`, `cache.importFromFile(file)`, `cache.registerModule(id, handlers)`, `cache.STORAGE_KEY`

`applyState()` (the single funnel for restore, file/shapefile/CSV/GeoJSON import and undo/redo) calls `App.ensureFeatureIds()` right after pushing features, next to the colorSeq counter advance, so every feature has a unique ID and the ID counters are past every ID in use.

Saves session state (points, lines, routes, polygons, buffer radii, form selections, LODES filename) to `localStorage` under key `"mat-session"`. Routes store full geometry + waypoints; no re-routing needed on restore. Restore runs automatically at end of map load. Save is debounced (500ms) and called after every state mutation. Reset clears localStorage and all app state. LODES data is NOT cached (too large); only the filename is stored as a re-upload hint.

**Merge history and exports:** `properties._mergedFrom` (Unmerge history, `js/core/merge.js`) is kept by every state path — localStorage autosave, undo/redo snapshots, session JSON (`exportToFile`, Save State, share link) — and omitted from every feature export: **JSON (Features only)** strips it via `App.mergeHistory.stripHistory` (`_stripMergeHistory` in `cache.js`), while CSV, KML and Shapefile/DBF only ever write a fixed attribute column list so they cannot include it. Any new feature-export path must strip it too. The per-type render functions that copy `feature.properties` into MapLibre sources (`lines.js`, `routes.js`, `polygons.js`, `points.js`, `editing.js` drag previews, `app.js` offset sources, `selection.js` highlight) skip `_mergedFrom`; the `duplicateX` functions build fresh property objects and never copy it.

`exportToFile()` serializes current state to a timestamped `.json` file and triggers a browser download. `importFromFile(file)` reads a JSON file (from a hidden `<input type="file">`), validates it, and applies the state — replacing all current features. Both use the same schema as localStorage (currently `version: 4`). Schema v1 sessions (with `stations` key) are automatically migrated to v2 (`points` key) on restore. **v3 → v4** (`docs/feature-color-system-plan.md`, one-time): for each line/route whose stored `properties.color` exactly matches the palette color its array position would have produced, clears it to `""` and stamps the equivalent `colorSeq`, so a feature drawn before the color cascade existed renders the identical color today but now follows the type default like everything drawn since; a polygon whose color matches the built-in default is cleared the same way. A color that doesn't match its palette slot was a deliberate user choice and is left alone as a per-feature override. Runs once per stored file — `migrateToCurrent` only applies it when `state.version === 3`, and the next save/export records the file at version 4, so re-importing an already-migrated file is a no-op.

`collect()`/`restore()` also carry `networkCrossingMajorSec`/`networkCrossingMinorSec` (`docs/walkshed-bands-and-crossing-penalties-plan.md` Phase 5) — additive fields mirroring the existing `networkSnapToleranceFt` pattern, restoring straight onto `App.networkSettings.crossingMajorSec`/`crossingMinorSec` and defaulting gracefully (0/off) when absent on an older session. No core schema bump.

`collect()`/`restore()` also carry `networkExcludedWayIds` (`docs/sidewalk-data-plan.md` Phase 4) — an additive field, empty array when absent on an older session. Unlike the other `networkSettings` fields, restore does **not** poke `App.networkSettings.excludedWayIds` directly: it calls `App.setExcludedWays(state.networkExcludedWayIds)`, the sanctioned write path, so `road-network.js`'s private `_excludedWays` Set — the object `buildGraph()` actually reads — stays in sync. No base network is loaded yet at restore time, so this is a cheap no-op rebuild that primes the exclusion set for whenever a network is next loaded. No core schema bump.

`collect()`/`restore()` also carry `layerStyles`/`mapPalette` (`docs/layer-color-customization-plan.md` Phase 3) — two more additive fields, same pattern: `collect()` deep-copies `App.layerStyles` (`{}` when absent) and `App.mapPalette` (`null` when absent); `restore()` deep-copies them back onto `App.layerStyles`/`App.mapPalette` when present, then calls `App.repaintStyledLayers()` once at the very end of `restore()` (guarded with a `typeof` check, since `cache.js` loads before the analysis modules register their repainters) so every layer on screen after a session reload repaints in the restored colors immediately, with no re-run required. Still no core schema bump — an older session file simply has neither key and every styleKey resolves to its module default.

`registerModule(id, { collect(mode), apply(data) })` — analysis modules call this at load time to opt into session persistence. `collect(mode)` returns a serializable object; `mode` is `"light"` (localStorage, skip heavy geometry) or `"full"` (file export, includes geos for choropleth restore). `apply(data)` restores state from a previously collected object. Module state is stored under `state.moduleState[moduleId]` in the JSON schema. The RF module registers as `"rf"` and persists weights, scenario forms, calibration metadata, per-route CDI, system demand result, shared-pool mode flag, and baseline uncertainty percentage (TPI geographies included in full export only). RF session schema is at **v4** (v4: every feature reference — `selectedCorridor` `"route:<id>"`, the calib/demand checklist filters `{ routeIds, lineIds }`, and the per-route CDI rows' `featureId` — is a stable ID; v1–v3 saved array indices and are converted in `restoreRfState` while the saved indices still match the live arrays; v1/v2 restored with backward-compat migration; v3 adds `sharedPoolMode`; `baselineUncertaintyPct` added gracefully — defaults to 0.25 when absent, no schema version bump needed).

### API — module-buffers.js
Shared analysis-buffer helper. Feature Area Analysis, Transit Coverage, Transit Propensity, Ridership Forecasting, and Corridor Scoring each expose a Buffer distance (mi) input plus a default-off **Use Display Buffers** toggle. The toggle disables the field and reads the selected currently displayed Feature Settings buffers; the default path builds a private buffer set from source geometry at the module's distance. Neither path mutates shared map buffers. See `docs/module-buffer-distance-plan.md` for the full design rationale.

`App.ANALYSIS_BUFFER_DEFAULT_MILES` (0.5 — one shared default for all five modules), `App.ANALYSIS_BUFFER_MIN_MILES` (0.05), `App.ANALYSIS_BUFFER_MAX_MILES` (5).

`App.foldAnalysisUnion(polys)` — folds an array of polygons into one union via `turf.union`; `null` for an empty array.

`App.buildAnalysisBuffer(feature, miles)` — `turf.buffer(feature, miles, {units:"miles", steps:64})`, `null` on failure.

`App.buildDisplayBufferSet(filter)` — returns the displayed route, line, and point buffers for an explicit selection, plus selected polygons unchanged, in the same `{ byType, union, get, count }` shape as `buildAnalysisBufferSet`. It honors Feature Settings and per-feature overrides exactly as the map does.

`opts.includeHidden` (default false) on `buildAnalysisBufferSet(filter, miles, opts)` and `buildDisplayBufferSet(filter, opts)` bypasses the `properties.hidden` skip; both return `hiddenCount: { included, skipped }`. With the flag, a hidden route/line/point gets an on-the-fly display buffer (per-feature `_bufferRadius`, else the `App.featureSettings` type default; walkshed substitution kept) that is never written to the shared display arrays. Every hide/show path (Layers tab, `App.bulkFeatures.setHidden`, Features pane eye/group eye/right-click, map right-click) now calls `App.notifyProject()`.

`App.readAnalysisBufferMiles(elOrId, fallback)` — reads + validates a buffer-distance input; accepts an element id (string), a DOM element, or any object exposing `.value` (so it's testable headless — the golden harness passes a plain `{value: "..."}` object). Returns `fallback` (default `ANALYSIS_BUFFER_DEFAULT_MILES`) when the value is missing, non-numeric, or outside `[MIN, MAX]`.

`App.buildAnalysisBufferSet(filter, miles, opts)` — the core builder. `filter = { routeIndices, lineIndices, pointIndices, polygonIndices }` (any key may be absent; always explicit arrays, consistent with the "never null means all" convention used by every module that calls this). Returns `{ byType: {route:{}, line:{}, point:{}, polygon:{}}, union, get(type, idx), count }`. Routes/lines get a plain `buildAnalysisBuffer`. Points prefer a cached walkshed (`attributes.serviceAreaType === "walkshed"` + `App.getPointWalkshed(pointIdx)` returns a polygon) over a circle at `miles`, unless `opts.preserveWalksheds === false` — a walkshed is a study-area *type*, not a distance. Polygons pass through **unbuffered** (already an area). Hidden features (`properties.hidden`) are skipped.

### API — choropleth.js
Shared choropleth rendering engine (`App.choropleth`), first consumer Feature Area Analysis. See `docs/feature-area-choropleth-plan.md` for the full design (curated ramp presets, apportioned-value display rule, Phase 3 migration of TPI/RF/Corridor Scoring onto this engine).

`App.choropleth.RAMPS` — curated ColorBrewer presets, each `{ label, colors5 }`: `blues` (default), `heat` (Yl-Or-Rd), `greens`, `rdbu` (diverging Rd-Bu).

`App.choropleth.computeClassBreaks(values, method, nClasses)` — pure, golden-tested. `values` is an array of finite numbers (caller pre-filters null/NaN); `method` is `"quantile"` (linear-interpolated rank position, "R-7" convention) or `"equal"`; `nClasses` defaults to 5. Returns `{ breaks, nEffective }` — `breaks` is `nClasses - 1` **inner** break values (class *i* covers `breaks[i-1] < v <= breaks[i]`), deduplicated so heavily tied data yields `nEffective < nClasses`; all-equal values yield `{ breaks: [], nEffective: 1 }`; empty input yields `{ breaks: [], nEffective: 0 }`.

`App.choropleth.buildStepColorExpr(prop, breaks, colors, noDataColor)` — pure. Builds a MapLibre `["step", ["get", prop], ...]` paint expression from `breaks`/`colors` (`colors.length` must equal `breaks.length + 1`), wrapped in a `["case", ["==", ["typeof", ["get", prop]], "number"], stepExpr, noDataColor]` so a non-numeric/missing property renders `noDataColor` (default `"rgba(200,200,200,0.35)"`) instead of silently taking the first class.

`App.choropleth.formatBreakLabels(breaks, min, max, fmt)` — pure. Returns one human-readable range label per class, lowest class first (e.g. `"1,204 – 2,410"`); `fmt` is a `(number) => string` callback, defaulting to `String`.

`App.choropleth.render(opts)` — map-facing; `opts = { id, features, valueProp, method, classes, ramp, breaks (optional manual/fixed override), beforeLayer, fillOpacity (default 0.55), lineColor/lineWidth/lineOpacity, hoverHTML (fn(props) => html string | falsy, or null for no hover), noDataColor }`. Creates or updates source `"<id>-choropleth"` and layers `"<id>-choropleth-fill"`/`"<id>-choropleth-line"` (create-once/`setData`-after, `beforeLayer` defaults to `"buffers-fill"` when present), attaching a shared hover `maplibregl.Popup` with cursor management on first creation. Keyed by `id` so multiple modules can each own one live choropleth instance without colliding (e.g. `"bas"` for Feature Area Analysis). Returns `{ breaks, colors, nEffective, min, max }` for the caller's legend.

`App.choropleth.remove(id)` — removes both layers + source and detaches hover listeners. Idempotent.

`App.choropleth.setVisible(id, visible)` — layout-visibility toggle (e.g. a "hide choropleth" checkbox). No-op if the layers don't exist.

`App.choropleth.fillLegend(containerEl, opts)` — fills the generic legend fragment (`projects/choropleth-legend.html`) once its floating-widget body has mounted (the Transit Travelshed fill-after-mount precedent). `opts = { title, labels, colors, note }`; rows fill top-to-bottom matching `labels`/`colors` order (lowest class first), unused rows hidden.

**Keyboard shortcuts** (two `keydown` listeners in app.js): the original handles `Delete`/`Backspace` on a feature selection (no vertex being edited, no input focused, no module panel or dialog open) opens the `App.bulkFeatures.confirmRemove` dialog; it also handles `Escape` (close popup / exit present / cancel measure), `Ctrl+Z`/`Ctrl+Shift+Z` (undo/redo), `Delete`/`Backspace` (delete selected vertex). `renderModuleState(opts)` — **shared module-state UI helper** every analysis popup uses to render its stale banner and empty/onboarding state identically. `opts = { statusEl, emptyEl, empty, hint, stale, status, onRerun }` where `statusEl`/`emptyEl` are a DOM element **or** an id string (resolved via `getElementById`; no-ops if absent, so it is safe to call from `update()` while the popup is closed). Precedence: (1) `empty:true` → show `emptyEl` (standardized `.rf-info-box` markup; `hint` is a string or `{ need, action }` — bold need line + muted action line) and hide the pill — this doubles as the first-open onboarding hint; (2) `status: { kind, message }` (`kind` = `running`|`done`|`error` or `""` neutral) → render the pill; (3) `stale:true` → render the `.rf-status-stale` pill with the standardized text "Inputs changed — re-run to update." plus a **Re-run button** that calls `onRerun`; (4) otherwise hide the pill. The pill preserves an existing `<span id="…StatusText">` when present. Each module keeps a thin local `setStatus(msg, kind)` that delegates here, plus (where applicable) a `showStale()` wrapper passing its run function as `onRerun` and a context-aware `emptyHint()`.

`renderModuleInputs(opts)` — **shared collapsible-inputs helper**, the sibling of `renderModuleState()`. `opts = { hostEl, collapsed, summary, label, onToggle }` where `hostEl` is the module's `.rf-settings-col` element **or** an id string. On the first call the host's existing children are moved into a `.module-inputs-body` wrapper and a clickable `.module-inputs-header` is prepended (moving nodes preserves listeners and element ids, so **no module markup changes are needed**). Later calls only update the summary text and collapsed state; omit `collapsed` to leave the current state alone. No-ops on a missing host, so it is safe to call while the popup is closed. Collapsed, the settings column becomes a full-width one-line bar above the results (`.rf-section-row:has(> .module-inputs-collapsed)` flips the row to a column) rather than a 280px stub beside them — this is what makes a narrow/stacked panel usable, since there the settings sit *above* the results and would otherwise push them below the fold. **Modules must collapse on a successful run only** — a failed or bailed-out run has to leave the inputs open, where the user needs them. Each module supplies an `inputsSummary()` returning a one-line description of what was actually run (e.g. `"15 min · 3.1 mph · 2 points"`), so a collapsed panel still answers "what am I looking at". Wired into `walkshed`, `transit-coverage` and `transit-travelshed`; the other modules adopt it as they are narrowed.

**Inputs vs. Settings — a naming convention, not enforced by code.** Analysis modules already split their controls two ways; this gives the split a name and a placement rule for new controls:
- **Inputs** — required selections the user must make. Live inline in the settings column, and collapse after a run (buffer distance, feature checklist, geography level, ACS year).
- **Settings** — optional or expert tuning. Live behind a button, a modal overlay, or a `<details>` block (Adjust Weights, Costing Settings, hull-detail `maxEdge`).

Nothing in the code checks this; it is a convention in the same spirit as the `.rf-`/`.tpi-` prefix rules.
