# Walkshed

Reference detail moved verbatim from `CLAUDE.md`. Read the code when this and the code disagree.

## Files

- **`walkshed.js`** — Walkshed module: 2-column popup (Settings | Results) that computes true street-network walking isochrones from placed Points using the offline road-network engine (`App.computeWalkshed` in `js/core/road-network.js`) — no external service. **Three time budgets** (`docs/walkshed-bands-and-crossing-penalties-plan.md` Phase 3, mirroring Transit Travelshed's `#tsBudget1/2/3`): `#wsMinutes`/`#wsMinutes2`/`#wsMinutes3` (min, defaults 15/30/blank, cap 60 each, blank = unused), walk speed mph (default 3.1; converted to km/h internally since the road-network engine's graph weights are km), point checklist (target set), advanced concave-hull `maxEdge` (displayed in **feet**, default 984 ft — Phase 7 of `docs/network-connectors-plan.md`; stored/persisted in `_settings.maxEdge` as **km**, `FT_PER_KM` converts at the UI boundary same as `walkSpeedMph`; a hull-geometry parameter, not a walking unit), an Advanced **connector snap tolerance (ft, default 50)** input (`#wsSnapTol`) that reads/writes the GLOBAL `App.networkSettings.snapToleranceFt` — not a module setting, shared with Transit Travelshed (`docs/network-connectors-plan.md` §2) — and on change calls `App.refreshNetworkConnectors()` and marks results stale. Two more Advanced inputs, **crossing delay — major/minor street (s, default 0 each)** (`#wsCrossMajor`/`#wsCrossMinor`), read/write the GLOBAL `App.networkSettings.crossingMajorSec`/`crossingMinorSec` the same way — also shared with Transit Travelshed — via `onCrossingChange()` (`App.cache.save()` + `markStale()`; no `refreshNetworkConnectors()` call, since no connector geometry changed, only the flood's cost function). A third Advanced line, **"Excluded streets: N — clear all"** (`#wsExcludedWaysCount`/`#wsClearExcludedWays`, `docs/sidewalk-data-plan.md` Phase 4 step 9), reads `App.networkSettings.excludedWayIds.length` — synced in `syncInputsFromSettings()` (so it refreshes whenever the popup opens, since exclusions are made by clicking the walk-network layer directly, which this popup has no other view into) — and its Clear button calls `App.setExcludedWays([])`. `activeBudgets()` reads `_settings.budgets`, drops blanks, dedupes, sorts ascending, and never returns empty (falls back to `[15]`); `readSettingsFromInputs()` sorts before storing so "first" and "smallest" stay identical by construction. A point's own `attributes.walkMinutes` override (supported in the data model, not yet exposed in the UI) still makes that point use a single budget instead of the module's list. `settingsKeyFor(pf)` folds every active budget, plus the two GLOBAL crossing-penalty seconds (`App.networkSettings.crossingMajorSec`/`crossingMinorSec`), into the cache key, not just one — they change the result but don't bump the network epoch, so without this the cache would serve stale polygons after a penalty change. `computeForPoint(pf)` floods once at the largest budget via `App.computeWalkshed(coords, maxBudgetKm, {maxEdge, budgetsKm, crossingPenaltyKm})` and stores the result as `entry.bands: [{minutes, polygon, area, nodeCount}]` (ascending); `crossingPenaltyKm` (`docs/walkshed-bands-and-crossing-penalties-plan.md` Phase 5, off by default) is built by `crossingPenaltyKmFor(speedKmh)` from the two global `App.networkSettings` seconds plus this point's own walk speed in km/h, via `window.WalkCost.penaltyKm(...)` — guarded with `typeof window.WalkCost !== "undefined"` so a missing script tag degrades to no penalty instead of throwing; absent/zero values are byte-identical to pre-Phase-5 output. `entry.polygon`/`area`/`reachableCount` alias the **smallest** band, so `getPointWalkshed()` needed no change — that smallest band is unconditionally the v2 study-area polygon. Renders a blue walkshed fill/line layer (one feature per band per point, largest pushed first so the smallest paints on top; colored by `["match", ["get","bandIdx"], 0, "#1e40af", 1, "#3b82f6", "#93c5fd"]`, the same data-driven pattern `network-joins-point` uses in `js/core/network-connectors.js`; per-point bands are ring-differenced largest-first so only each band's newly-reachable ring paints, not the full cumulative disc) + a green reachable-segments correctness layer (drawn at the largest budget only); visibility of each is controlled independently from the Layers panel (`walkshed-fill` and `walkshed-seg` rows — Phase 1; there is no in-popup toggle) — hiding the `walkshed-seg` row also hides the legend's "Reachable streets" row (`#wsLegendRowSeg`), since a hidden layer with a visible legend swatch would be misleading; the same repainter is registered under both the `walkshed` and `walkshed-seg` styleKeys (`fillWalkshedLegend()` reads the segment layer's live `visibility` layout property) and `layers-panel.js`'s eye-icon handler calls `App.repaintStyledLayers(entry.styleKey)` after every toggle so the legend updates live while it's on screen. **Flatten overlapping walksheds** — a display-only toggle in the `walkshed-fill` Layers-panel drawer (`spec.flattenOption` in `js/core/layer-palettes.js`'s `LAYER_STYLES`, persisted as `App.layerStyles.walkshed.flatten` through the same `App.setLayerStyle` cascade every other per-layer override already uses, so it needs no new persistence code) — re-renders the FILL only as one polygon per distinct minutes value, unioned across every point that uses it and differenced against the union of every smaller value, so the shortest walkshed wins wherever two points' walksheds overlap; `bands[]` itself (and every study-area/export consumer that reads it) is untouched by this. The OUTLINE — `walkshed-line`, now its own source `walkshed-line-src` rather than sharing `walkshed-fill`'s single source with it — always keeps the un-flattened, per-point ring-differenced boundaries, so an overlap the fill hides stays visible as a preserved outline. Off by default; toggling it fires the same `walkshed`/`walkshed-seg` repainter registered above, which re-renders geometry (`renderWalkshedLayers(_lastEntries)`), not just paint, whenever results are on screen — see `buildFlattenedFillFeatures()`. With flatten on, most of the preserved per-point outlines now sit INSIDE the merged fill rather than on its real edge, so `outlineStyle()` also drops `walkshed-line`'s paint from its normal `{width:2, opacity:0.9}` to a deliberately faint `{width:1, opacity:0.12}` (`WS_OUTLINE_NORMAL`/`WS_OUTLINE_FLATTENED`) — still findable, not competing with the fill for attention; flatten off restores the normal weight. floating legend, a per-point-per-band results table (`#wsResultsTable`: Point/Band/Walkshed area (mi²/km²)/Nodes/Time, point name and compute time shown only on each point's first row), a **connection-report footer line** (`#wsConnReport`, `docs/network-connectors-plan.md` Phase 6 — only shown when at least one walk connector exists, sourced from `App.getConnectorReportSummary()`; styled with the module's warning color when a connector end isn't joined), a **sidewalk coverage footer line** (`#wsCoverageReport`, `docs/sidewalk-data-plan.md` Phase 3 — right after the connection-report line, only shown when a network is loaded, sourced from `App.getSidewalkCoverageSummary()`, same warning-color convention), GeoJSON export (one feature per band per point, each carrying `minutes`/`bandIdx`). `inputsSummary()` reads e.g. `"15 / 30 min · 3.1 mph · 2 points"`; `computeRequiredExtent()` sizes its download-prompt circles from the **largest** budget. The "Use as study areas" button (`#wsUseStudyArea`) label is rebuilt on every settings change from `activeBudgets()[0]` — e.g. "Use 15-min walkshed as study areas" — with a `title` tooltip warning that changing the smallest budget changes every downstream module's study area; `useAsStudyAreas()` itself needed no logic change. **v2 study-area integration:** each Point carries `attributes.serviceAreaType` (`"walkshed"` vs default circular buffer); the module computes+caches a walkshed polygon per point (keyed by pointIdx, invalidated on move / settings / network-epoch change) and exposes `App.getPointWalkshed(pointIdx)` + `App.ensurePointWalksheds()`. `points.js rebuildBuffers()` substitutes the cached walkshed for the circle when a point is flagged, so every study-area consumer (Buffer-Area Summary, Census, LODES, TPI, Title VI, FTA, corridor pickers) uses the walkshed with no per-module changes. Session persistence: settings always persist, schema **v3** (`budgets` array; v1/v2 sessions storing a single `minutes` value migrate to a one-entry budget list on restore; the existing v1 `walkSpeedKmh` → `walkSpeedMph` migration is unchanged). The last Compute run's polygons + reachable-streets geometry additionally persist in **full mode only** (file Save/Load State, not the localStorage autosave) — `collect(mode)` includes `lastEntries` (each entry's `bands` + `reachableSegments`) only when `mode === "full"`, and `apply()`'s `restoreEntries()` rebuilds `_walkshedCache`/`_lastEntries` and calls `renderWalkshedLayers()`/`showWalkshedLegend()` immediately, with no road network or Calculate click needed — the same full-mode-only pattern Corridor Scoring's `lastSummary` uses, and left out of the light/localStorage autosave so a settings tweak doesn't grow every autosave payload. A restored polygon is still gated by `getPointWalkshed()`'s `settingsKey` check like any cache entry, so it naturally falls back to a circular buffer for downstream study-area consumers once the road network is reloaded (a fresh epoch never matches the saved key) rather than being trusted as current. A localStorage-only restore (plain page reload) still shows no polygons until Calculate is run, same as before.

- **`walkshed-popup.html`** — Walkshed popup body: 2-column layout (Settings | Results). Settings has a **three-input time-budget row** (`#wsMinutes`/`#wsMinutes2`/`#wsMinutes3`, defaults 15/30/blank — `docs/walkshed-bands-and-crossing-penalties-plan.md` Phase 3, reusing Transit Travelshed's `.ts-budget-row`/`.ts-budget-input` shared classes rather than duplicating them) plus a walk-speed input, an advanced `maxEdge` + connector-snap-tolerance details block that also carries the Phase 5 **crossing delay — major/minor street (s)** inputs (`#wsCrossMajor`/`#wsCrossMinor`, default 0 each — off) with help text on the node-uniform (not turn-aware) approximation, a point checklist (`#wsPointList`), and a Calculate button (disabled + `#wsNetWarn` shown when no road network is loaded). The reachable-streets layer's visibility is controlled from the Layers panel's "Walkshed — reachable streets" row, not an in-popup toggle — the old `#wsShowSegments` checkbox was retired (Phase 1) because it fought with the Layers panel over the same layer's `visibility` property. Results has the standard `#wsStatus.rf-status` pill, a per-point-per-band results table (`#wsResultsTable`), and "Use as study areas" (dynamic label, e.g. "Use 15-min walkshed as study areas") / "Export GeoJSON" buttons, plus `#wsEmptyState.rf-info-box`.

- **`walkshed-legend.html`** — Walkshed legend: walkshed-fill swatch + reachable-streets swatch (reuses `.tpi-legend-*`).

## API

### API — walkshed.js (analysis module)
Registers module `"walkshed"`. Public: `App.getPointWalkshed(pointIdx)` (validated cached walkshed polygon Feature, or null when absent/stale — consumed by `rebuildBuffers`), `App.ensurePointWalksheds()` (synchronously compute any walkshed-flagged points missing/stale in the cache; returns `{ computed, cached, failed, warnings }`). Module-local cache keys entries by `pointIdx` with a `settingsKey` of `coords|minutes|speed|maxEdge|networkEpoch`, so moving a point, changing walk parameters, or reloading the network invalidates the entry automatically. `App.dropPointWalksheds(ids)` frees cache entries for removed points (`pointIdx` values; Feature Merge calls it — stale entries were already ignored by `getPointWalkshed`, which requires the point to exist).
