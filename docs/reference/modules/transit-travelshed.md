# Transit travelshed

Reference detail moved verbatim from `CLAUDE.md`. Read the code when this and the code disagree.

## Files

- **`transit-travelshed.js`** — Transit Travelshed module: 2-column popup (Settings | Results) that computes walk → wait → ride drawn transit routes/lines → walk isochrones from a clicked map origin, with at most one transfer, rendered as 1-3 banded rings. Origin is a probe pattern (an in-popup "Pick origin on map" button arms a one-shot `App.drawMode === "ts-origin"` map click, NOT an `App.points` feature — textboxes.js's `_initDrawMode` is the precedent), rendered as a single draggable-free `maplibregl.Marker`. Settings: 1-3 time budgets (min, default 15/30/blank), walk speed (mph, default 3.1), analysis day + time (`App.getEffectiveServiceBands` selects each feature's active band; no band or blank/0 frequency excludes the feature — disclosed, not an error), wait model (max initial wait min 10, boarding penalty min 1 — capped-initial/uncapped-transfer split per `docs/transit-travelshed-plan.md` Appendix A, with an info toggle), **walk limits** (`shedMode` select — `"transit"` (default; walking to/between/from transit is capped) vs `"door"` (walking may use the whole time budget — v1's uncapped behavior), plus max access/egress/transfer walk (mi, defaults 0.5/0.25/0.25) with an info toggle; the three cap inputs disable while `"door"` mode is selected — see `docs/transit-travelshed-v2-walk-caps-plan.md`), assumed stop spacing (mi, default 0.25, for routes/lines with no associated stop Points), a routes+lines checklist (annotates schedule-less features), an Advanced hull-detail `maxEdge` (displayed in **feet**, default 984 ft — Phase 7 of `docs/network-connectors-plan.md`; stored/persisted in `_settings.maxEdgeKm` as **km**, same `FT_PER_KM` UI-boundary conversion as Walkshed), and an Advanced **connector snap tolerance (ft, default 50)** input (`#tsSnapTol`) that reads/writes the GLOBAL `App.networkSettings.snapToleranceFt` — not a module setting, shared with Walkshed (`docs/network-connectors-plan.md` §2) — and on change calls `App.refreshNetworkConnectors()` and marks results stale. Real stops come from Points whose `attributes.associatedRoutes` reference the feature (resolved by scanning `routeIdx`/`lineIdx`, never the array index); synthetic stops are sampled otherwise. A per-stop walk-flood cache (`stopKey|networkEpoch|budgetKm`) is filled chunked-async via `App.computeWalkCostMap`; in `"transit"` mode the origin flood radius is capped at `min(budgetKm, accessCapKm)` and the stop flood radius at `min(budgetKm, max(egressCapKm, transferCapKm))` — shrinking per-stop flood work roughly 50-90× at typical settings — while `"door"` mode floods both at the full max-budget radius as in v1, so one flood still serves every band and re-run at unchanged settings. `ensureFloods()` yields every 5 stops or every ≥50ms of work (not after every single stop — a nested `setTimeout(0)` costs real time, roughly 4ms each, across hundreds of stops) while still updating the "Walking from stop x/y" status every stop. Each fresh `computeWalkCostMap` call returns a `snapMs`/`floodMs` split (see the `road-network.js` entry's "Snap acceleration" note); `ensureFloods` sums these across every fresh stop flood, `runTravelshed()` adds the origin flood's own split, logs the totals to the console, and shows them in the results footer (`snap N ms · flood N ms`) — added after a diagnostic found city-scale snapping (an unindexed per-call scan of every network segment) was the actual bottleneck behind slow "Walking from stop x/y" progress, not the flood radius. `window.Travelshed.computeArrivalTimes` (js/core/travelshed.js) does the layered-flood arrival-time math on plain JSON built from that cache, passing the three walk-leg caps (minutes) only in `"transit"` mode. Bands are pure thresholds over one flood (`Travelshed.bandNodeSets`) but that now drives only the per-band **node counts** shown in the results table — per-band **geometry** is a union of per-cluster polygons (§2.4 cluster-union polygonization): one for the origin/access walk blob, plus one per alighting stop (from the engine's `alightings` array), each independently capped and polygonized via `App.polygonizeNodeSet` then combined with `App.foldAnalysisUnion` — used in both modes, so a single hull can no longer bridge unreachable space between disjoint stop clusters. The resulting per-band union is ring-differenced largest-first (innermost stays solid; a `turf.difference` failure falls back to the un-differenced polygon) into a 3-class Blues fill/line layer. Prompt-to-download: Calculate first checks whether the loaded network's recorded download extent (`App.getRoadDownloadExtent`) contains the analysis's required extent (origin's walk circle — access-capped in `"transit"` mode, full-budget in `"door"` mode — ∪ a walk buffer around each selected feature — capped at the larger of the egress/transfer limits in `"transit"` mode, full-budget in `"door"` mode); if not (or no network loaded), it offers a scoped `App.fetchRoadNetworkForExtent` download and auto re-runs on success — a file-imported network (extent unknown) gets a soft warning instead and is not blocked. Results: per-band area (mi²/km²) + node count + compute stats table, a per-route disclosure panel (band used, wait math, real vs sampled stop counts, direction/loop handling, or exclusion reason) with a footer disclosing the active walk caps (or "Door-to-door — walk uncapped" in `"door"` mode), a **connection-report footer line** (`docs/network-connectors-plan.md` Phase 6 — same `App.getConnectorReportSummary()`-sourced line as Walkshed, appended via `connectionReportHTML()`), a **sidewalk coverage footer line** (`docs/sidewalk-data-plan.md` Phase 3 — same `App.getSidewalkCoverageSummary()`-sourced line as Walkshed, appended via `coverageReportHTML()` right after `connectionReportHTML()`), a floating legend with dynamic per-band labels, GeoJSON export (band rings + origin + methodology metadata, including `shedMode` and the three walk-cap values). Session persistence: settings-only schema **v2** (origin, budgets, wait model, spacing, hull detail, shed mode + the three walk caps, `selectedRouteIds` keyed by the stable routeIdx/lineIdx counter so restore survives index shifts; v1 payloads restore cleanly since the new fields fall back to `DEFAULT_SETTINGS`) — geometry is not persisted, so a restored session's export stays disabled until Re-run.

- **`transit-travelshed-popup.html`** — Transit Travelshed popup body: 2-column layout (Settings | Results), settings column copied from the Transit Coverage/Walkshed shells. Settings has the origin block (`#tsPickOriginBtn`/`#tsOriginLabel`/`#tsClearOriginBtn`), 3 budget inputs (`#tsBudget1/2/3`), walk speed, day+time selectors, wait-model inputs with an info toggle (`#tsWaitInfoBtn`/`#tsWaitInfoText`), a "Walk limits" block (`#tsShedMode` transit/door select, `#tsAccessWalk`/`#tsEgressWalk`/`#tsTransferWalk` cap inputs (mi), info toggle `#tsWalkCapsInfoBtn`/`#tsWalkCapsInfoText`), stop spacing, a routes+lines checklist (`#tsRouteList`) with Select all/Clear, an Advanced `maxEdge` details block, network state (`#tsNetWarn`/`#tsCoverageWarn`/`#tsDownloadBtn`), and the Calculate button (`#tsRunBtn`). Results has the standard `#tsStatus.rf-status` pill, a per-band table (`#tsResultsTable`), a per-route disclosure panel (`#tsRouteDetail`), an Export GeoJSON button (`#tsExportBtn`), and `#tsEmptyState.rf-info-box`.

- **`transit-travelshed-legend.html`** — Transit Travelshed legend: 3 rows reusing `.tpi-legend-*` (ids `#tsLegendRow0/1/2` + `#tsLegendLabel0/1/2`); the module fills each band's "≤ N min" label and hides unused rows after mount.
